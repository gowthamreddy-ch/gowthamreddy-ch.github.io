ReviewLens — Evidence-First Code Review

Working prototype

A local AI code-review lab that connects changed-line findings to executable evidence. Compare reviewers, inspect context, and verify one authorization fixture against original code, a PR and a candidate fix.

Working local prototype with synthetic TypeScript/JavaScript PRs and a separate, opt-in verification workflow. Screenshots captured November 15, 2026 show the current interface and saved results. Verification evidence is from October 13; the AI comparison is from October 8. GitHub integration, public app hosting and held-out evaluation remain future work.

Explore the screenshots, walkthrough and measured results below. The interactive application currently runs locally; contact me for a demonstration.

Inspect the change and review the finding

Choose a synthetic backend PR and compare four AST rules, diff-only AI or AI with explicit context. Each finding includes a valid added-line location, an exact excerpt, severity, reasoning, a proposed fix and a suggested test. Invalid proposals remain visible as rejections.

02

Make the model’s context inspectable

Context mode sends the selected diff and the helper files and policy shown in the interface. The saved ownership review demonstrates why a signed-in user is not necessarily authorized to delete a project. Review modes analyze source without executing it; executable verification is a separate workflow.

03

Verify the authorization finding

For the built-in admin-guard fixture, an opt-in worker runs the same frozen, hand-authored regression test twice against each version: original, PR and candidate fix. The PR allowed a non-admin and failed the anonymous-request check; the original and candidate fix passed all three checks, including legitimate admin access.

04

Keep a review record and a human decision

Run history preserves input snapshots, reviewer modes, processing status and findings. Feedback and approval are stored with each run. Only approved review drafts can be exported locally. Verification records retain test and source hashes, the runner image ID, execution observations and blocked or inconclusive outcomes.

05

Compare reviewers and preserve failures

The ten-case development comparison found four of five seeded bugs with the static rules and no clean-case flags. Both AI modes flagged three of five clean cases. Category/location matching overstated semantic quality; the separate AI-assisted audit records incorrect reasoning and missing-context failures. Independent human scoring is still needed.

02 / Engineering

Engineering evidence

Problem and scope

The product hypothesis is that small teams need fewer speculative review comments and clearer supporting evidence. This local lab focuses on authorization, input validation and async/error-handling defects in TypeScript/JavaScript backends. No customer research or productivity gains are claimed.

My role and contribution

Built the React/TypeScript workspace, Node API, SQLite migrations, persistent review and verification queues, static and AI reviewers, exact-location validation, feedback and approved-draft export. Added the allowlisted Docker verification runner, frozen test contracts, repeat-trial classification and persistent evidence artifacts.

Architecture and data flow

One modular application serves the UI and API on loopback. A bounded review worker parses source or calls the OpenAI Responses API. A separate verification queue executes only the approved built-in handler in disposable Docker containers, without network, host mounts or model credentials. SQLite retains run inputs, decisions, immutable plans and results.

Technology choices and tradeoffs

Use a transparent static baseline before adding model complexity. Bind verification to source, test and plan hashes; use the same test for every version and retain an admin positive control. Containers are non-root with read-only roots, dropped capabilities and resource limits. This narrow fixture runner is not a general service for executing untrusted repositories.

Results and evaluation

All 17 automated tests passed on November 15, covering review validation, persistence, retries, API boundaries, frozen verification plans, false-proof prevention and runner constraints. The saved October 13 Docker run reproduced the fixture defect across two PR trials; original and fix passed all three checks twice. The frozen ten-case AI comparison remains mixed: static found 4/5 seeded bugs; both AI modes flagged 3/5 clean cases. It is synthetic development evidence, not real-world accuracy.

Limitations and next steps

Single-user loopback lab; no authenticated multi-tenant service or GitHub App integration. Verification supports one exact authorization fixture with a hand-authored test and fix, not AI-generated tests or arbitrary PR execution. A response double checks handler behavior, not a database or full authorization stack. Held-out evaluation, independent semantic scoring and a developer usability study remain pending.

03 / Research roadmap

Next investigation

Proposed extension

Research question

When does executable evidence help a developer accept or dismiss an AI finding, and when should verification remain inconclusive?

Planned method

Use the completed authorization workflow as a starting point. Define reviewed behavior contracts, preserve blocked and inconclusive results, and prepare a developer study before expanding to assisted test creation or real repositories. Keep the existing reviewer benchmark frozen; obtain independent judgments before held-out evaluation.

What I would measure

  • Time to accept or dismiss a finding and tests developers choose to keep
  • Independently judged verification correctness, false proof and inconclusive outcomes
  • Execution latency, resource use and reviewer precision on a separately frozen benchmark

The usability study has not been conducted. One reproduced fixture does not establish general verification accuracy, developer time savings or production security. Preserve failures and do not tune on held-out results.

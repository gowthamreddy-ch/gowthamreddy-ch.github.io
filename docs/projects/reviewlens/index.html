ReviewLens — Evidence-First Code Review

Working prototype

A working code-review lab with static and live AI reviewers, exact changed-line evidence, persistent history, and human-approved comment drafts. Its evaluation preserves false positives and unsupported reasoning.

Milestone 1 works locally with synthetic TypeScript/JavaScript PRs. Live AI was verified with a separate server-side key. GitHub App integration, public deployment and the held-out benchmark remain future work; no GitHub comments are published.

Explore the screenshots, walkthrough and measured results below. The interactive application currently runs locally; contact me for a demonstration.

01 / Walkthrough

System walkthrough

A sequence of workflows to explain the project.

01

Inspect the change and review the evidence

Choose a synthetic backend PR, inspect its diff, and run four transparent AST rules or a live AI reviewer. Every displayed finding includes an added-line location, exact excerpt, severity, reasoning, proposed fix and verification test. Invalid proposals are retained as rejections.

02

Supply context without granting execution

Context mode sends only the selected diff and the explicitly displayed helper files and policy to OpenAI. The app parses repository text without executing it. Useful/not-useful feedback and approved local drafts are saved with each run; GitHub publishing is disabled.

03

Compare results and preserve the failures

The ten-case development comparison found four of five seeded bugs with the static rules and no clean-case flags. Both AI modes flagged three of five clean cases. Category/location matching overstated semantic quality; a separate AI-assisted audit records the wrong reasoning and missing-context failures. Independent human scoring is still needed.

02 / Engineering

Engineering evidence

Problem and scope

The product hypothesis is that small teams need fewer speculative review comments and clearer supporting evidence. This local lab focuses on authorization, input validation and async/error-handling defects in TypeScript/JavaScript backends. No customer research or productivity gains are claimed.

My role and contribution

Built a React/TypeScript dashboard, Node HTTP API, SQLite migrations and persistent review queue, worker-based static and live AI analysis, strict location/evidence validation, feedback, draft approval and export. Added tests, a CI definition, synthetic fixtures, reproducible measurement scripts, screenshots and a demo protocol.

Architecture and data flow

One modular application serves the UI and API on loopback. A bounded worker parses source using the TypeScript compiler API or calls the OpenAI Responses API with structured output. SQLite stores input snapshots, run state, results and decisions. Secrets stay server-side; submitted code is never executed.

Technology choices and tradeoffs

Use a small transparent static baseline before adding model complexity. Compare diff-only and explicitly supplied context using the same pinned model and validator. Deduplicate submissions, retry only selected transient failures, and mark interrupted work as failed when cost may be unknown. Keep source provenance distinct from semantic truth.

Results and evaluation

Ten automated tests passed, covering output validation, persistence, retry limits, idempotency and local API boundaries. Desktop and 390-pixel mobile workflows were checked. Across ten authored development cases, static produced 4 findings and found 4/5 seeded bugs; diff-only produced 10 findings and context 8, both flagging 3/5 clean cases. A conservative AI-assisted semantic audit accepted 4/4, 3/10 and 4/8 respectively; it is not independent human scoring. Twenty benchmark API calls had an estimated combined cost of $0.010932. Full conditions and failures are linked.

Limitations and next steps

A single-user synthetic lab, not a production GitHub reviewer. No authentication, verified webhooks, installation permissions or publishing allowlist is implemented yet. Repository-scoped storage is not multi-tenant authorization. Held-out evaluation and independent semantic review remain pending. Small development measurements cannot establish real-world accuracy, security protection or time savings. Local links work on this laptop only.

03 / Research roadmap

Next investigation

Proposed extension

Research question

When does explicit repository context improve supported findings, and when does the reviewer still speculate?

Planned method

Freeze the current development reports, refine abstention on development cases, obtain independent semantic judgments, then lock code and prompt hashes before evaluating the reserved family-disjoint split.

What I would measure

  • Finding precision and known-bug recall under an evidence-and-mechanism rubric
  • False positives on clean changes and unsupported missing-context claims
  • Raw location accuracy, validator rejections, latency and token-cost estimates

Seeded authored cases are not real-world GitHub evidence. Preserve failures and report uncertainty; do not tune on held-out results and label them fresh validation.

FindWise — Product Discovery & Commerce

Working prototype

A home-office storefront with explicit budget and specification filters, product comparison, and persistent carts backed by an ASP.NET Core API.

Milestone 1 is working locally: catalog, keyword search, filters, comparison, and guest carts. All 18 products, prices, and inventory are synthetic. No real purchases occur. Accounts, checkout, membership benefits, and price alerts are planned.

Explore the screenshots, walkthrough and measured results below. The interactive application currently runs locally; contact me for a demonstration.

01 / Walkthrough

System walkthrough

A sequence of workflows to explain the project.

01

Find equipment within your constraints

Browse 18 monitors, keyboards, and desk chairs. Search by keywords, filter by category, maximum regular price, monitor size, resolution, and stock, then sort by price or name. A 27-inch 4K filter with a $250 budget returns two monitors. Empty results preserve the constraints; shoppers choose what to remove.

02

Inspect specifications and availability

Each product page shows consistent specifications, stock, regular pricing, and reference Plus pricing. Out-of-stock items cannot be added to the bag. Plus prices are informational at this stage; guest carts use regular prices.

03

Compare a shortlist

Select up to three products and compare prices, availability, and specifications side by side. Selections persist in the browser. View 27 and Studio 27 share screen specifications but differ in price and connectivity, including USB-C power delivery.

04

Review a cart with server-owned prices

Add products, change quantities, remove items, and reload to retain the cart. The API calculates amounts and rejects invalid quantities or stock limits. Two View 27 monitors total $458. Tax and delivery remain explicitly uncalculated; the cart does not reserve inventory or place an order.

05

Use the store on a small screen

The mobile catalog has a collapsible filter panel and responsive cards. The bag stacks its item controls and summary. Focused checks covered keyboard filter activation and layouts at 320px and 390px; this is not a claim of a complete accessibility audit.

02 / Engineering

Engineering evidence

Problem and scope

Product discovery becomes frustrating when requirements are hard to express and alternatives obscure the budget. FindWise explores a controlled home-office store with explicit constraints. This is a product hypothesis, not validated customer research. The catalog uses authored fictional data, without retailer scraping.

My role and contribution

Implemented a Next.js and TypeScript storefront, modular ASP.NET Core API, PostgreSQL schema and seed, persistent guest carts, comparison, responsive states, and 13 database-backed integration tests. Added reproducible setup, a local launcher, an architecture diagram, a CI workflow definition, and a measured search baseline.

Architecture and data flow

Next.js proxies same-origin requests to ASP.NET Core catalog and cart modules. Parameterized SQL reads PostgreSQL products; integer cents represent prices. An opaque HttpOnly cookie identifies a guest cart whose token hash is stored in the database. Transactional cart-row locking serializes edits. Migrations run explicitly under a database advisory lock.

Technology choices and tradeoffs

Start with a keyword baseline and hard filters before adding search intelligence. Keep budget and specification constraints intact. Let the server own prices and stock validation; use absolute quantities so a repeated update does not add items twice. Use a small synthetic catalog to make behavior reproducible. Keep services modular without adding unnecessary infrastructure.

Results and evaluation

All 13 PostgreSQL-backed API tests passed, covering guest isolation, price tampering, quantity and stock checks, retry-safe updates, cross-origin rejection, and concurrent cart edits. Production builds passed. On 12 developer-judged tuning queries, baseline NDCG@5 was 0.4869 and Recall@5 was 0.4500 across 10 positive intents; both expected-empty cases were correct. Eight held-out queries remain unused. Direct local API latency was p50 1.95 ms and p95 2.42 ms: 18 products, concurrency 1, 20 samples per query, excluding browser rendering. These are baseline findings, not search improvements or production scaling results.

Limitations and next steps

Keyword search does not yet tolerate typos or parse natural-language budgets. No authentication, admin uploads, payments, orders, active membership, watchlists, price history, or notifications exist yet. Cart checks do not prove checkout inventory safety. GitHub CI and deliberate API-outage recovery remain unverified. No public deployment, user study, conversion result, or recorded video is claimed. Next: identity, admin inventory, and test checkout; then measured search improvements and resilient member alerts.

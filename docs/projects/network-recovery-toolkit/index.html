Network Configuration and Recovery Toolkit

Working prototype

A working simulated network lab with integrity-checked backups, configuration drift, state-bound recovery approval, bounded retries, rollback, and monitoring adapters.

Working Evidence Lab rebuild. Recovery changes only a simulated device. Local SNMP and monitoring were verified in September 29 reports; physical hardware, remote Ansible execution and production recovery are not claimed.

01 / Walkthrough

System walkthrough

A sequence of workflows to explain the project.

01

Inspect drift and prepare recovery

Inspect interface and BGP health, create a backup with an integrity hash, or inject a named lab fault. Compare the current configuration with the approved baseline before selecting an allowlisted recovery action.

02

Approve the exact proposed change

Preview the diff and expected health. The proposal is tied to a state hash, expires after five minutes, and is consumed once. Applying it requires explicit approval; failed verification triggers rollback after bounded attempts.

02 / Engineering

Engineering evidence

Problem and scope

Configuration recovery should expose what will change, what success means, and what happens when verification fails. The project demonstrates those controls in an isolated simulated device.

My role and contribution

Implemented snapshots and hashes, drift diffs, state-bound proposals, approval/replay/staleness protection, bounded recovery attempts, rollback and an event timeline. Added read-only SNMP collection, a loopback SNMP agent, Prometheus exporters, Grafana configuration, and Ansible/CI definitions.

Architecture and data flow

The browser and Python CLI operate a local simulated-state engine. A recovery proposal binds an allowlisted action to the exact state. Separate exporters expose lab and SNMP metrics to Prometheus and Grafana. Hardware-facing adapters are separate from the simulated recovery engine.

Technology choices and tradeoffs

Require a preview and state-specific approval. Save pre-change state and verify health before declaring success. Keep retries bounded and restore original state on failure. Label real loopback SNMP transport separately from simulated device values.

Results and evaluation

The September 29 report records 40 successful recoveries across 20 paired automated lab trials. Median operation times were approximately 0.0229 s and 0.0196 s for the two lab workflows; they are not human recovery times. The 71-test suite included a real loopback SNMP UDP exchange. Saved monitoring evidence shows two exporters scraped and a nine-panel Grafana dashboard. Today’s browser check confirmed a recovery preview and disabled application before approval; existing device state was preserved.

Limitations and next steps

No physical router or remote recovery was accessed. Portable Windows monitoring was used because Docker was unavailable; alert rules were validated separately from the metrics-only runtime. Ansible and remote GitLab jobs were not executed. Historical résumé time reductions are not attributed to this rebuild. Recorded live evaluations date to September 29, 2026; fresh API availability and billing were not retested for this portfolio update. Saved examples are hand-authored and labeled. Data and network devices are synthetic. No customer study, production performance, physical-device recovery, or public deployment is claimed. Source stays private.

03 / Research roadmap

Next investigation

Proposed extension

Research question

How does a recovery workflow respond when a dependency fails partway through an approved action?

Planned method

In an isolated test environment, inject selected failures into a documented recovery sequence. Record retry behavior, rollback outcomes, and the final observable state.

What I would measure

  • Recovery and rollback outcomes
  • Adherence to retry limits
  • Actions visible in the audit record
  • Cases requiring human intervention

This is a proposed extension. Tests would be limited to explicitly defined scenarios in an isolated environment.
